Sulabha candidate search - architecture

Sulabha UI takes the place of the Angular UI. Part 1 (bulk upload of the S3 resumes) is new; part 2 (candidate search) is the API as built today.

Overview: bulk upload and search

Part 1 loads the resumes from S3 through queues; part 2 is the regular candidate search. Both use the same API and database.

Part 1 in sequence: bulk upload (proposed)

Sulabha sends S3 file links with a candidate id for each. The Intake Lambda queues one event per record; the Ingest Lambda sends each to the API. Errors go to an error queue that Sulabha can query.

  • /upload-resume/{id} is new. It runs what today's /upload_resumes_bulk runs per file (extract text, duplicate check, suggest the form, build the profile, save), but takes the candidate id from Sulabha instead of generating a UUID.
  • Sending the same id again updates that candidate, so a queue retry never creates a second record.
  • A duplicate resume is skipped, not reported as an error.

Part 2 in sequence: candidate search (as built)

The LLM reads the query only on a cache miss; matching and ranking run in code against Postgres.
