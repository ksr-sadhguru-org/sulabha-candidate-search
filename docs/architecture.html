Sulabha candidate search - architecture

Sulabha UI takes the place of the Angular UI. Part 1 (bulk upload of the S3 resumes) is new; part 2 (candidate search) is the API as built today.

Overview: bulk upload and search

Part 1 loads the resumes from S3 through queues; part 2 is the regular candidate search. Both use the same API and database.

Part 1 in sequence: bulk upload (proposed)

Sulabha sends S3 file links with a candidate id for each. The Intake Lambda queues one event per record; the Ingest Lambda sends each to the API, which downloads the file from S3, builds the search profile and saves it. A failed record is written to Postgres, and Sulabha reads the failures from the API.

  • /upload-resume/{id} is new. It takes the candidate id from the URL (today's bulk upload generates a UUID) and an S3 link, then does the whole job: extract the text, duplicate check, build the profile, save. The API needs read access to the bucket.
  • /failed-resumes is new too. It reads a new failed_resumes table, so no separate Lambda or error queue is needed.
  • Sending the same id again updates that candidate, so a queue retry never creates a second record. A duplicate resume is skipped, not recorded as a failure.
